## 1. Latar Belakang & Visi

### Mengapa v3?

SuperSep v2.0 berhasil membangun pipeline 10-agent yang bekerja, namun memiliki gap fundamental:

| Versi | Model | Kelemahan |
|---|---|---|
| v1.0 | 5 specialist agents | Setiap agent terbatas pada domain-nya saja |
| v2.0 | 10 agents, stage pipeline | Agent 1-5 tetap specialist; agent 6-10 hanya coding section berbeda |
| **v3.0** | **10 omniscient agents** | **Setiap agent punya pengetahuan penuh, dibedakan oleh thinking style** |

Di v2.0, saat /gassep berjalan, Agent 1 hanya menulis routing, Agent 6 hanya menulis CI/CD — mereka tidak saling terhubung secara intelektual. Di v3.0, setiap agent melihat seluruh problem dari perspektif mereka sendiri, lalu saling sanggah dan saling melengkapi.

### Visi: Ensemble Intelligence

> "10 senior engineer berbeda diminta me-review PR yang sama. Masing-masing punya opini kuat. Hasilnya jauh lebih baik daripada 1 engineer yang me-review seluruh PR sendirian."

Tujuan akhir: SuperSep v3.0 menghasilkan output yang menandingi model premium seperti Claude Fable 5.1, GPT-6 Astra, DeepSeek-V4.1-Flash — bukan dengan model yang lebih mahal, melainkan dengan memaksimalkan 10 Gemini Pro accounts melalui ensemble intelligence dan adversarial debate.

## 2. Filosofi Desain

### Ensemble Intelligence vs Specialist Division

**Specialist Division (v2):**
```
Input -> Agent 1 (routing) -> Agent 2 (UI) -> ... -> Agent 10 (QA) -> Output
```
Setiap agent mengerjakan bagian berbeda. Gap antar bagian tidak terdeteksi. Tidak ada debat.

**Ensemble Intelligence (v3):**
```
Input -> [Agent 1..10 semua melihat FULL problem] -> Debat -> Merged Master Output
```
Setiap agent menghasilkan solusi lengkap. Kekurangan satu agent ditutup oleh sembilan lainnya.

### Prinsip Utama

1. **No Domain Walls** — Tidak ada agent yang "hanya bisa" satu hal
2. **Cognitive Diversity** — Perbedaan thinking style, bukan perbedaan domain
3. **Zero Gap Tolerance** — Setiap celah yang ditemukan di Round 2 WAJIB ditutup di Round 3
4. **Always Finish** — Council tidak pernah berhenti di tengah jalan; self-healing jika ada kegagalan
5. **Transparent Contribution** — Setiap agent wajib berkontribusi; jika gagal, tercatat secara jelas

## 4. Protocol 3-Round Omni

### Adaptive Task Routing (Pre-Round)

Sebelum Round 1, `triage.py` mendeteksi jenis task:

```
TASK_TYPE: brainstorm | ui_ux | slicing | coding | fix_error | security | optimization | mixed
```

### Round 1 — Parallel Full Solutions

**Semua 10 agent berjalan simultan via asyncio.gather.**

Output per agent (JSON terstruktur):
```json
{
  "agent_id": "agent_1",
  "persona": "The Conservative Guardian",
  "solution": "Solusi lengkap dan mendetail...",
  "rationale": "Kenapa memilih pendekatan ini...",
  "risks": ["Risk 1...", "Risk 2..."],
  "improvements": ["Hal yang bisa lebih baik..."],
  "artifacts": "Code / design / plan sesuai task_type..."
}
```

### Round 2 — Cross-Agent Critique & Improvement Patches

**Semua 10 agent berjalan simultan via asyncio.gather.**
Setiap agent membaca 9 solusi lain dan menghasilkan:

```json
{
  "agent_id": "agent_3",
  "strengths_to_adopt": [{"from": "agent_6", "insight": "..."}],
  "weaknesses_found": [{"in": "agent_2", "issue": "...", "fix": "..."}],
  "improvement_patches": ["Patch 1...", "Patch 2..."],
  "conflicts_to_resolve": [{"between": ["agent_4", "agent_5"], "resolution": "..."}]
}
```

### Round 3 — Merged Master Synthesis

**Single synthesizer — timeout 10 menit.**

Aturan ketat NON-NEGOTIABLE:
1. Setiap agent WAJIB berkontribusi setidaknya 1 elemen ke output final
2. Setiap `weakness_found` WAJIB ditutup
3. Setiap `conflict_to_resolve` WAJIB diselesaikan dengan reasoning eksplisit
4. Setiap `improvement_patch` dievaluasi dan diintegrasikan jika valid
5. Zero gap, zero mismatch

**Output format per task_type:**

| TASK_TYPE | Output |
|---|---|
| brainstorm | Master Architecture Blueprint (Markdown) |
| ui_ux | Design System Spec + Component Hierarchy |
| slicing | Complete component code + design tokens |
| coding | Production-ready merged code files |
| fix_error | Root cause + complete fix + prevention |
| security | Threat model + remediation + hardened code |
| optimization | Performance audit + optimized code |
| mixed | Composite output sesuai komponen terdeteksi |

## 5. Self-Healing Council Architecture

### Skenario 1 — 1 Agent Gagal (Toleransi Normal)
- Council lanjut dengan 9 solusi
- Synthesizer Round 3 mengkompensasi perspektif yang hilang
- Catatan transparan di output

### Skenario 2 — 2+ Agent Gagal (Self-Healing Mode)

**Step 1 — Save Checkpoint**
```
memory/projects/<name>/checkpoints/round1_partial_<timestamp>.json
```

**Step 2 — Agent Substitution**
Agent yang gagal diambil alih oleh agent lain yang sudah selesai:
```
"Kamu adalah [persona agent yang gagal].
Berikan solusi lengkap untuk task ini dari perspektif tersebut..."
```
Substitusi berjalan simultan. Maksimum 3 percobaan.

**Step 3 — Merge & Continue**
Semua perspektif (asli + substitusi) digabung → Round 2 & 3 berjalan normal.

**Step 4 — Checkpoint Cleanup**
File checkpoint dihapus setelah output final berhasil.

### Jaminan Output

| Kondisi | Perilaku |
|---|---|
| 10/10 sukses | Full output — 10 perspektif asli |
| 9/10 sukses | Full output — synthesizer kompensasi 1 perspektif |
| 8/10 atau kurang | Self-Healing aktif — agent substitution |
| Substitusi juga gagal | Checkpoint disimpan, user diberitahu untuk resume |
| **Council tidak pernah berhenti** | **Self-healing selalu mencari jalan untuk menyelesaikan** |

## 6. Performance & Reliability Architecture

### Configuration (.env)

```env
# Router
ROUTER_BASE_URL=http://localhost:20128/v1
ROUTER_API_KEY=<key>
MODEL=5_gemini_3.8_flash_by_antigravity_v2
ROUTER_CONCURRENCY=10

# Council
COUNCIL_QUORUM=9
AGENT_TIMEOUT_SECONDS=300
SYNTHESIS_TIMEOUT_SECONDS=600
RETRY_MAX_ATTEMPTS=5

# Recovery
CHECKPOINT_DIR=memory/projects
MAX_SUBSTITUTION_ATTEMPTS=3
```

### Retry Schedule (Exponential Backoff)

```
Attempt 1: langsung (0s)
Attempt 2: tunggu 2 detik
Attempt 3: tunggu 5 detik
Attempt 4: tunggu 10 detik
Attempt 5: tunggu 20 detik
Total maksimum wait: ~37 detik per agent
```

### Connection Pooling

```python
limits = httpx.Limits(max_connections=10, max_keepalive_connections=10, keepalive_expiry=60)
timeout = httpx.Timeout(connect=30.0, read=300.0, write=30.0, pool=10.0)
```

Shared AsyncClient — eliminasi TCP handshake overhead saat 10 agent fire simultan.

### Circuit Breaker

```
5 request berturut-turut gagal dalam 30 detik → Circuit OPEN
→ Auto-reset setelah 60 detik
→ User diberitahu dengan pesan diagnostik jelas
```

### Wall-Clock Time Estimate

```
Round 1: asyncio.gather(all 10)  →  ~15-30 detik (parallel)
Round 2: asyncio.gather(all 10)  →  ~15-30 detik (parallel)
Round 3: 1 synthesizer           →  ~30-60 detik (sequential)
─────────────────────────────────────────────────────────────
Total estimasi: 60-120 detik untuk full council
```

## 7. Struktur Kode

### File Map & Tanggung Jawab Tunggal

```
orchestrator/
├── agent_runner.py      Round 1 saja: run_all_solutions() → list[AgentSolution]
├── council.py           Round 2 + 3: run_cross_critique() + synthesize_merged_master()
├── router.py            HTTP transport: retry, pooling, circuit breaker
├── recovery.py [NEW]    Self-healing: checkpoint + agent substitution
├── triage.py            Task type detection + project memory
├── pipeline.py          Koordinasi stage saja
├── state.py             Pipeline state management
├── learner.py           Knowledge distiller
└── stages/
    ├── ui_stage.py
    ├── arch_stage.py
    ├── ensemble_code_stage.py  [REDESIGNED: 10 full impl → merge]
    └── healing_stage.py
```

### Dataclasses

```python
@dataclass
class AgentSolution:
    agent_id: str
    persona: str
    status: Literal["success", "failed", "substituted"]
    solution: str
    rationale: str
    risks: list[str]
    improvements: list[str]
    artifacts: str
    raw: str
    error: str | None = None

@dataclass
class AgentCritique:
    agent_id: str
    persona: str
    status: Literal["success", "failed"]
    strengths_to_adopt: list[dict]
    weaknesses_found: list[dict]
    improvement_patches: list[str]
    conflicts_to_resolve: list[dict]
    raw: str
    error: str | None = None
```

## 8. Cara Penggunaan (Usage Guide)

### /mikirsep — Brainstorming & Architecture

```bash
/mikirsep <task atau ide>
python main.py --stage arch --task "Buat sistem autentikasi JWT"
python main.py --stage ui --task "Dashboard analytics" --image ./mockup.png
```

Flow: triage → Round 1 (10 full plans) → Round 2 (10 critiques) → Round 3 (Master Blueprint) → simpan ke memory

```bash
/gassep <task>
```

Flow: load blueprint → Round 1 (10 full impls) → Round 2 (critiques) → Round 3 (merged code) → tulis ke disk → self-healing build


## 10. Known Constraints & Roadmap

### Keterbatasan Saat Ini

- **Model ceiling:** gemini-3.8-flash memiliki batas reasoning; ensemble mengkompensasi tapi tidak 100% setara untuk task sangat complex
- **Context window Round 2:** Mengirim 9 solusi penuh ke setiap agent — jika solusi sangat panjang bisa mendekati batas context window
- **Token volume:** Sangat besar per sesi — konsekuensi yang diterima secara sadar demi kualitas output

### Roadmap Berikutnya

- [ ] Agent Memory Persistence — agent ingat pattern proyek sebelumnya
- [ ] Streaming Output — tampilkan Round 1 solutions realtime saat agent selesai
- [ ] Agent Reputation System — track akurasi historis, beri bobot lebih ke yang track record baik
- [ ] Multi-modal Round 1 — agent terima screenshot/design sebagai input
- [ ] Parallel Stage Execution — ui_stage + arch_stage berjalan bersamaan
